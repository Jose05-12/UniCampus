1. Descripción del proyecto

UniCampus es una aplicación web para administrar las actividades académicas de la institución (talleres, conferencias, seminarios, cursos, encuentros y ferias). Permite registrar y mantener las actividades, consultarlas con búsqueda y filtros, gestionar las inscripciones de los estudiantes controlando los cupos y recoger reseñas y valoraciones de quienes participaron.

El proyecto parte del formulario de registro de actividades construido en cortes anteriores y lo transforma en una solución organizada en tres capas (presentación, negocio y datos) con el patrón MVP en la capa de presentación, conectada a SQL Server mediante ADO.NET con consultas parametrizadas.

2. Arquitectura de tres capas

La solución UniCampus.sln tiene cuatro proyectos. Cada capa es un proyecto independiente y las referencias siguen un único sentido: Web → BLL → DAL → SQL Server. El proyecto UniCampus.Entities contiene las clases de datos que viajan entre capas y no depende de ninguna otra.

2.1 Responsabilidades por capa

CapaProyectoResponsabilidadNo hace
PresentaciónUniCampus.WebMostrar formularios y resultados, capturar eventos, convertir texto a tipos, mostrar mensajes de éxito/validación/error.No escribe SQL ni referencia la capa de datos.
NegocioUniCampus.BLLValidar campos y reglas (cupos, fechas, estados, permisos), coordinar repositorios y devolver un ResultadoOperacion comprensible.No usa controles ASP.NET ni System.Web.

3. Patrón Model-View-Presenter (MVP)

MVP se aplica dentro de la capa de presentación; no reemplaza las tres capas. Cada página tiene tres piezas:

  • Vista: la página .aspx y su code-behind. Implementa una interfaz (por ejemplo IActividadesView), solo lee y escribe controles y delega cada evento en el Presenter.
  • Presenter: clase (por ejemplo ActividadesPresenter) que recibe las acciones, convierte los datos, llama a la capa de negocio y le dice a la vista qué mostrar. No contiene SQL ni controles ASP.NET.
  • Modelo: los servicios de la BLL y las entidades de UniCampus.Entities.

4. Flujo de una operación: registrar una actividad

  1. El administrador completa el formulario y pulsa Guardar actividad.
  2. El evento btnGuardar_Click llama a ActividadesPresenter.Guardar().
  3. El Presenter lee los valores de la vista, valida el formato (números, fechas, horas) y construye una entidad Actividad.
  4. ActividadService.Guardar verifica que el usuario sea administrador, normaliza los textos y ejecuta Validar (obligatorios, longitudes, tipo existente, fechas, horas, cupos, estado, duplicados). Si hay errores devuelve un ResultadoOperacion con la lista de mensajes y no se toca la base de datos.
  5. Si todo es válido llama a ActividadRepository.Insertar.
  6. El repositorio ejecuta un INSERT parametrizado y devuelve el identificador generado.
  7. El Presenter muestra el mensaje de éxito, selecciona la nueva actividad y recarga el listado.

5. Base de datos y diagrama entidad-relación

Se reutilizó el modelo trabajado en el curso: la entidad central es ActividadAcademica, clasificada por TipoActividad. Para cubrir inscripciones y reseñas se usan Usuario (con rol Administrador o Estudiante, sin duplicar tablas de personas), Inscripcion y Resena, que relacionan usuarios con actividades.

5.3 Control de cupos con solicitudes simultáneas

InscripcionRepository.Inscribir ejecuta toda la inscripción dentro de una transacción serializable. Primero bloquea la fila de la actividad con WITH (UPDLOCK, ROWLOCK); así, si dos estudiantes intentan tomar el último cupo al mismo tiempo, la segunda solicitud espera a que termine la primera y, al contar de nuevo los inscritos, recibe "sin cupos". Si algo falla se hace Rollback.

using (var tx = cn.BeginTransaction(IsolationLevel.Serializable))
{
    // 1. Bloquear la actividad y leer su cupo
    "SELECT Cupos FROM dbo.ActividadAcademica WITH (UPDLOCK, ROWLOCK) WHERE ActividadId = @A;"
    // 2. ¿Ya está inscrito?   3. ¿Quedan cupos?   (si no → tx.Rollback())
    // 4. INSERT INTO dbo.Inscripcion (ActividadId, UsuarioId) VALUES (@A, @U);
    tx.Commit();
}

6. Validaciones y seguridad

AspectoImplementación
Validación en el servidorTodas las reglas se validan en la BLL (ActividadService.Validar, InscripcionService, ResenaService). Las validaciones del navegador son solo una ayuda; si se omiten, el servidor rechaza los datos igualmente.
Doble barreraLas reglas críticas (cupos, fechas, duplicados, calificación) también existen como restricciones en SQL Server.
SQL parametrizadoTodas las consultas usan SqlParameter con tipo y tamaño. No se concatena texto del usuario en SQL. La búsqueda con LIKE escapa los comodines (Conexion.PatronLike).
ContraseñasHash PBKDF2-SHA256 (10 000 iteraciones) con salt aleatorio por usuario y comparación en tiempo constante (SeguridadPassword).
Sesión y permisosEl usuario se obtiene de la sesión del servidor (SesionUsuario); las páginas heredan de PaginaBase, que exige sesión iniciada. Los servicios verifican el rol antes de cada operación.
Errores controladosLos Presenter capturan las excepciones, registran el detalle técnico en App_Data/Logs y muestran al usuario un mensaje entendible sin información interna. customErrors redirige a Error.aspx.
ConfiguraciónCadena de conexión con autenticación integrada de Windows (sin usuario ni contraseña). Cookies HttpOnly y SameSite=Lax; cabeceras X-Content-Type-Options, X-Frame-Options y Referrer-Policy.
Repositorio.gitignore excluye bin, obj, .vs, archivos de usuario y logs.

11. Conclusiones

  • Separar la solución en presentación, negocio y datos permitió que cada parte tenga una sola responsabilidad: las páginas ya no contienen SQL y las reglas de negocio están en un único lugar, lo que facilita probarlas y modificarlas.
  • El patrón MVP dejó las páginas .aspx enfocadas en mostrar información; la lógica de coordinación vive en los Presenter, que dependen de una interfaz de vista y no de controles concretos.
  • Validar en el servidor y repetir las reglas críticas como restricciones de SQL Server crea dos barreras: aunque se salte la interfaz, los datos inválidos no llegan a la base.
  • Las consultas parametrizadas eliminan el riesgo de inyección SQL, y la transacción con bloqueo de fila resuelve el problema de sobrecupo cuando varias personas se inscriben a la vez.
  • Reutilizar el modelo entidad-relación existente y ampliarlo solo con las tablas necesarias (inscripciones y reseñas) evitó duplicar entidades y mantuvo la coherencia con el trabajo de los cortes anteriores.
  • El uso de Git y GitHub con ramas, commits descriptivos y un README completo permite que cualquier persona descargue, configure y ejecute el proyecto siguiendo las instrucciones.
